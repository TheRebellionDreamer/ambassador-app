# Ambassador App — общий план работ

> Документ для всей команды. Работа разделена: **BE** — один разработчик, **FE** — второй (амбассадор, автор прототипа).
> Изменения в контракте FE↔BE (раздел 5) обсуждаем вместе, прежде чем менять код.

## 1. Зачем

Амбассадор табачного бренда ходит по заведениям (кальянным), представляет новые вкусы и ведёт учёт:
какие заведения, кто там работает, что пробовали, что понравилось, сколько табака осталось.

Прототип (`~/Downloads/map-notes`: ванильный JS + Leaflet + localStorage) работает только на одном
устройстве и теряет данные при очистке браузера. Переписываем с нуля:

- данные на сервере, доступ с любого устройства;
- **работа без интернета** с отправкой изменений при появлении связи;
- сейчас пользователь один, потом **команда амбассадоров с ролями**.

## 2. Функции (спецификация из прототипа)

**Карта**

- Метки заведений, долгий тап по карте создаёт заведение (адрес — обратным геокодингом).
- Геолокация «где я».
- На карте подсвечены точки маршрутов на сегодня и будущие даты.

**Заведение**

- Название, адрес, координаты, категория (A+, A, B, C, C-), лояльность к бренду.
- Торговый представитель дистрибьютора (справочник, автодополнение).
- Часы работы и предпочтительное время визита (диапазоны дней + время).
- Контакты сотрудников: имя, должность, Telegram/телефон (кликабельные).
- «Что хотели бы попробовать» (wishlist), дистрибьюторы, с которыми работает заведение.

**Визит**

- Дата, «сколько кальянов в сутки отдаёт заведение», общий отзыв, отношение к продукту.
- Дегустации: аромат из каталога, реакция (👍 / 😐 / 👎), «будет в заказе» (да/нет), комментарий.
- Статистика по заведению: среднее, мин/макс, последнее значение кальянов в сутки; все дегустации.

**Склад**

- Остатки ароматов в чашках у амбассадора, приход, ручная корректировка.
- Каждая дегустация автоматически списывает 1 чашку; если дегустацию удалили, чашка возвращается.
- Подсветка «заканчивается» (< 3 чашек).

**Маршруты и план**

- Маршрут на дату: список заведений со статусом «запланировано / посетил / пропустил».
- Отметка «посетил» открывает или создаёт визит (связь точки маршрута с визитом).
- План на месяц: цель N посещений, прогресс.

**Команда (позже)**

- Приглашения, роли, назначение заведений амбассадорам.
- Отчёты для менеджера: по ароматам (дегустации, % «понравилось», «в заказе»), по амбассадорам.
- Экспорт в Excel.

### Что исправляем по сравнению с прототипом

| Проблема прототипа                                                             | Решение                                       |
| ------------------------------------------------------------------------------ | --------------------------------------------- |
| Маршруты ссылаются на заведение по индексу → после удаления указывают на чужое | UUID везде                                    |
| Списание со склада необратимо (флаг `deducted`)                                | Журнал движений склада, компенсирующие записи |
| Дата визита — свободный текст                                                  | Тип `date`                                    |
| Визиты и маршруты не связаны                                                   | `RoutePoint.visitId`                          |
| XSS через `innerHTML` / `onclick`                                              | React экранирует сам                          |
| Нет бэкапа, одно устройство                                                    | Сервер + Postgres + ежедневный бэкап          |

## 5. Контракт FE↔BE ⚠️ главная точка стыковки

### 5.1 Общие правила

- **Все id — UUID v4, их генерирует клиент** (`crypto.randomUUID()`), иначе нельзя создавать записи оффлайн.
- Схемы сущностей и запросов sync лежат в `@ambassador/shared` (zod). BE валидирует ими запросы, FE — формы и ответы.
  Менять схемы можно только через PR в `packages/shared`, который видят оба.
- Даты: `date` — строка `YYYY-MM-DD`, время — ISO 8601 UTC.
- Удаление мягкое: у записи проставляется `deletedAt`, клиент получает её через pull и удаляет у себя.

### 5.2 Auth

| Метод                                                   | Назначение                                                 |
| ------------------------------------------------------- | ---------------------------------------------------------- |
| `POST /auth/login` `{ email, password }`                | → `{ accessToken, user }`, refresh-токен в httpOnly cookie |
| `POST /auth/refresh`                                    | по cookie → новый `accessToken` (refresh ротируется)       |
| `POST /auth/logout`                                     | отзывает refresh                                           |
| `GET /me`                                               | пользователь + memberships (организация, роль)             |
| `POST /orgs/:id/invites`, `POST /invites/:token/accept` | приглашения (этап «Команда»)                               |

Access-токен живёт 15 минут, refresh — 30 дней. Запросы идут с `Authorization: Bearer <token>`, refresh — с `credentials: 'include'`.
Открытой регистрации нет: первый пользователь (OWNER) создаётся сидом.

### 5.3 Синхронизация

**Push** — отправить локальные изменения:

```http
POST /sync/push
{
  "mutations": [
    { "mutationId": "uuid", "entity": "place", "op": "upsert", "data": { "id": "uuid", ... } },
    { "mutationId": "uuid", "entity": "tasting", "op": "delete", "data": { "id": "uuid" } }
  ]
}
→ { "results": [ { "mutationId": "uuid", "status": "ok" | "rejected", "reason": "..." } ] }
```

- Порядок мутаций сохраняется, мутации применяются по очереди.
- Повторная отправка того же `mutationId` безопасна: сервер вернёт прежний результат (идемпотентность).
- Если мутация отклонена (`rejected`: нет прав, невалидные данные), клиент убирает её из outbox. Правильное состояние придёт при следующем pull.
- Конфликты решаются по правилу «побеждает последняя запись», на уровне строки. Склад конфликтов не имеет (см. 5.4).

**Pull** — получить изменения с сервера:

```http
GET /sync/pull?since=<cursor>&limit=1000
→ { "changes": { "place": [...], "visit": [...], ... }, "cursor": "123", "hasMore": false }
```

- `cursor` — непрозрачная строка (внутри серверная версия). При первом запуске `since=0`.
- Возвращаются в том числе удалённые записи (с `deletedAt`).
- Клиент вызывает pull, пока `hasMore = true`.

**Сущности sync** (`entity`): `place`, `placeContact`, `salesRep`, `distributor`, `placeDistributor`,
`visit`, `tasting`, `flavor`, `stockMovement`, `route`, `routePoint`, `monthlyTarget`.

**Когда синхронизироваться (FE):** при старте, по событию `online`, после локальной правки (с debounce)
и по таймеру раз в 1–2 минуты. Сначала push, потом pull.

### 5.4 Склад

- Остаток = сумма `delta` по `StockMovement` (holder, flavor). Записи журнала **никогда не меняются и не удаляются**.
- Клиент сам создаёт движения:
  - создание дегустации → `{ reason: 'TASTING', delta: -1, tastingId }`;
  - удаление дегустации → `{ reason: 'TASTING', delta: +1, tastingId }`;
  - смена аромата в дегустации → `+1` старому аромату и `-1` новому;
  - приход → `RECEIPT`, ручная правка → `ADJUSTMENT`.
- Сервер проверяет: у `TASTING` delta = ±1, `tastingId` указан, holder — текущий пользователь.

## 6. Модель данных (Postgres / Prisma)

Синхронизируемые таблицы содержат `id uuid`, `orgId`, `createdAt`, `updatedAt`, `deletedAt?`, `version bigint`
(глобальная последовательность, её выставляет триггер в БД; на ней строится pull).

| Таблица             | Поля (кроме служебных)                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `Organization`      | name                                                                                                                |
| `User`              | email, passwordHash, name                                                                                           |
| `Membership`        | userId, orgId, role (`OWNER` / `MANAGER` / `AMBASSADOR`)                                                            |
| `Invite`            | orgId, email, role, tokenHash, expiresAt, acceptedAt                                                                |
| `RefreshToken`      | userId, tokenHash, expiresAt, revokedAt                                                                             |
| `Place`             | name, address, lat, lng, category, loyalty, wishlist, workHours (json), visitHours (json), salesRepId?, assigneeId? |
| `SalesRep`          | name, contact                                                                                                       |
| `PlaceContact`      | placeId, name, position, contact                                                                                    |
| `Distributor`       | name                                                                                                                |
| `PlaceDistributor`  | placeId, distributorId                                                                                              |
| `Visit`             | placeId, userId, date, hookahsPerDay?, notes, attitude                                                              |
| `Tasting`           | visitId, flavorId, reaction?, willOrder?, comment                                                                   |
| `Flavor`            | name, line? (каталог бренда)                                                                                        |
| `StockMovement`     | holderUserId, flavorId, delta, reason, tastingId?, comment                                                          |
| `Route`             | userId, date, name                                                                                                  |
| `RoutePoint`        | routeId, placeId, position, status (`PLANNED` / `VISITED` / `SKIPPED`), visitId?                                    |
| `MonthlyTarget`     | userId, month (`YYYY-MM`), target                                                                                   |
| `ProcessedMutation` | mutationId (PK), userId, status, reason                                                                             |

`workHours` / `visitHours`: `[{ fromDay: 'MON', toDay: 'FRI', from: '12:00', to: '02:00' }]`.

## 7. Роли и права

| Данные                                 | AMBASSADOR             | MANAGER                              | OWNER           |
| -------------------------------------- | ---------------------- | ------------------------------------ | --------------- |
| Заведения, контакты, ТП, дистрибьюторы | чтение и запись        | чтение и запись                      | чтение и запись |
| Визиты, дегустации                     | читает все, пишет свои | всё                                  | всё             |
| Каталог ароматов                       | чтение                 | чтение и запись                      | чтение и запись |
| Склад                                  | свой                   | читает все, корректировки и передачи | всё             |
| Маршруты, план                         | свои                   | читает все                           | всё             |
| Пользователи, приглашения              | —                      | приглашает амбассадоров              | всё             |

**Допущения** (можно пересмотреть):

- заведения общие для организации;
- склад у каждого амбассадора свой (табак носит с собой), передача между людьми — движение `TRANSFER`.

## 8. Деплой

Один VPS, `docker compose`:

- `caddy` — HTTPS и раздача собранного FE;
- `api`;
- `postgres`;
- ежедневный `pg_dump` в объектное хранилище.

CI на GitHub Actions: lint, typecheck, тесты, сборка образов, деплой по ssh.

## 9. Этапы

Обозначения: **BE** / **FE** / **Общее**. 🔗 — точка стыковки: BE отдаёт, FE подключает.

### Этап 0. Каркас ✅

- [x] Монорепо, `packages/shared` с enum-ами, NestJS (config, prisma, health, swagger, логи), Vite + React + Mantine + PWA.

### Этап 1. Данные и контракт

- [ ] **BE:** Prisma-схема всех таблиц, миграция, SQL-триггер `version`, сид (организация, OWNER, каталог ароматов).
- [ ] **Общее:** zod-схемы сущностей и sync-контракта в `packages/shared`.
- [ ] **FE:** Dexie-схема по этим же сущностям + таблица `outbox`; каркас экранов и навигации.

### Этап 2. Auth

- [ ] **BE:** login / refresh / logout / me, guards, роли.
- [ ] **FE:** экран входа, хранение access в памяти, автообновление по refresh, защищённые роуты.
- 🔗 BE отдаёт рабочий `/auth/*` и тестового пользователя из сида.

### Этап 3. Синхронизация

- [ ] **BE:** `POST /sync/push` (идемпотентность, права, advisory lock), `GET /sync/pull` (курсор, удаления), e2e-тесты.
- [ ] **FE:** sync-воркер: outbox → push → pull → применение в Dexie; индикатор «не синхронизировано: N».
- 🔗 Сценарий: создать заведение оффлайн → включить сеть → запись появилась на втором устройстве.

### Этап 4. Функции

- [ ] **FE:** карта (Яндекс), заведения, визиты с дегустациями, склад, маршруты, план.
- [ ] **BE:** handlers и проверки прав для каждой сущности, валидация склада.

### Этап 5. Прод

- [ ] **BE:** Dockerfile, compose для прода, бэкапы, CI.
- [ ] **FE:** PWA (установка, оффлайн-оболочка), иконки.
- [ ] **Общее:** домен, HTTPS, ключ Яндекс Карт для домена.

### Этап 6. Команда

- [ ] **BE:** приглашения, назначение заведений, отчёты, экспорт в Excel.
- [ ] **FE:** управление командой, экраны отчётов.
